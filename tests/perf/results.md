# WP25 perf results

Generated by `npm run test:perf` (`tests/perf/canvas-lag.perf.spec.ts`), against the Vite dev
server (not a production build -- see the WP25 report for why that's still representative here).
Each row is one action on a canvas of the given card count; frame times are sampled with an
in-page `requestAnimationFrame` loop running concurrently with the action, "React commits" comes
from a React DevTools hook stub (no app source touched to get this number), and
"getNodeTypePorts evals" is the dev-only counter in `client/pipeline/nodes/nodeTypes.tsx`.

Targets at 150 cards (from the WP25 guide): pan p95 < 20ms, card drag p95 < 25ms, typing has no
dropped frames (no single frame far above the ~16.7ms/60fps budget).

Pan is measured zoomed in (z=1, not "zoom to fit") and sweeping ~1500px per leg, so cards
actually cross the viewport edge -- at "zoom to fit" over 150 cards nothing is ever off-screen,
so panning would never exercise the off-screen-card culling fix (WP25 part 3).

## Summary

The biggest, cleanest fix is visible in two numbers:

- **"run chain of 5 cards" -> getNodeTypePorts evals**: before scaled with total card count on
  the canvas (120 / 270 / 480 at 30 / 80 / 150 cards) even though the run only touches 5 cards --
  running a tiny chain was re-evaluating every other card's ports. After: flat at 18 regardless
  of card count. This is the direct, measured effect of per-shape atoms for field anchors and
  run state (see "top causes" below) -- a change local to one card no longer invalidates every
  other card's `getNodePorts` cache.
- **"drag one card 3s" -> longest frame** at 80 cards: before, 3566.5ms (a 3.5 second freeze --
  exactly the "quite lagging" the owner reported); after, 50.0ms.

p95 numbers also drop across the board at 80/150 cards (e.g. select-all+deselect p95 at 150:
549.9ms -> 466.6ms; run-chain p95 at 150: 283.4ms -> 83.3ms), though "select-all + deselect"
is still well above the 150-card budget in both runs -- see "still slow" below.

One regression worth naming honestly: pan's *longest single frame* at 150 cards got worse
(16.8ms before -> 366.7ms after), and `getNodeTypePorts` evals during pan went from 0 to
819. This is the culling fix's own cost: as a card crosses the viewport edge, its culled flag
flips, `NodeBody` swaps between the placeholder and the real `Component`, and that triggers one
port re-evaluation for *that* card (not every card, per the atom fix) -- but the first time a
culled chart card scrolls back into view, mounting echarts (dynamic `import()` + `init()`) is
expensive enough to show up as a single janky frame. Steady-state cost is lower (idle off-screen
cards no longer render), but re-entering the viewport is not free. Not fixed in this pass --
flagged under "still slow".

Planner re-run after keeping field-port anchors while a card is culled (useFieldPortAnchor.ts): a card scrolling back no longer re-measures every row, so the 150-card pan longest frame drops from 366.7ms to 100ms. Single runs; frame numbers vary run to run.
